## 自然请求如何落到范围

### 应触发

- “请把 `<资料根>` 文件夹及其下面所有文件添加到知识库。”默认列举全部用户内容文件，排除版本控制内部元数据和依赖/构建/cache/temp 派生树，逐件 read/distill/skip。
- “把 `<工作区>/Project Alpha` 加入知识库。”先判目录类型；代码项目未说“所有文件”时只冻结高价值入口和重要文档。
- “把 `<工作区>/Project Alpha` 及其下所有文件都收录。”所有用户内容源码也进 scope/inventory，源码默认 index-only 合法 skip，除非用户要求逐源码分析。
- “把 `<文件路径>/README.md` 整理到知识库。”建立唯一文档 collection，单文件索引并产一份独立结果。
- “只给这九个仓库建导航，先不要整理正文。”只执行 G0–G2；不扫描纳入第十个目录。
- “更新已登记的 `<资料根>`，但排除 `drafts/`。”按旧范围与当前现场做增量，在 G1 明确排除规则和数量。

### 不触发

- “先看看这个文件写了什么。”只是阅读。
- “构建报错了。”只是当前问题处理。
- “扫描时发现旁边还有一个目录。”没有明确收录意图。
- “这个历史规则现在还有效吗？”是查询和现场核验，不是建库。

“加入知识库”只承诺本流程的路径导航、逐文件台账、独立整理和项目综合，不等于写入长期知识/经验条目。若用户还明确要求保存跨项目结论，先完成全部适用文件阶段，再报告可保存的结论、原始文件依据和边界。

## 阶段失败矩阵

| 阶段 | 典型失败 | 当场动作 | 不允许 |
|---|---|---|---|
| G0 | 数据根不可读、路径越界 | 停止受影响项，保留现有内容 | 换到未授权目录绕过 |
| G1 | 混入低频路径、类型证据冲突、group 不唯一 | 重列 included/excluded 和证据 | 从结果反推范围或凭 Git 猜类型 |
| G2 | scope/inventory/manifest 差异或重复 owner | 只写索引字段；下游五列留空并重跑 G2 | 写 “pending” 占位或提前伪造读取状态 |
| G3 | 文件不可解析、权限失败、identity 不一致 | 写完整 read/skipped/reason；distilled/output 仍可空 | 改写证词、伪装成无价值 |
| G4 | source 错配、缺 portable-v1、模板空话、要点不足 | 补齐 distilled/output；纯内容错只返工当前文件 | 用 summary、legacy 模式或目录概述冒充单文件结果 |
| G5 | 已有 summary 漏链、跨组链接 | 修当前综合并全量复验链接 | 强制给零结果或无综合价值的组造空 summary |
| G6 | 项目专属结论被当作跨项目结论 | 不建议保存或补足边界 | 为凑数量生成条目 |
| G7 | 孤儿、编码、安全或集合差异 | 回最早受影响阶段顺序重跑 | 用“报告已解释”替代硬失败清零 |

机器结构检查与人工内容检查必须同源：scope、inventory、manifest 和单文件 metadata 是结构真值；正文事实由实际原文件支撑。校验失败信息只能指向重读、重建输出或诚实未完成，不能引导修改原始读取证据。

## 实际场景

### 场景 1：迁移历史资料集

用户只说：“请把 `<资料根>` 文件夹及其下面所有文件添加到知识库。”现场回读发现既有权威清单登记 706 个文件、21 个分组、19 份历史项目卡，格式混有 DOCX、XLSX、PDF、SQL，也有敏感和不可解析文件。

应做：

1. G1 以用户全量要求和既有权威 inventory 共同冻结 706 条及 `path→group`，不能因为只有两条既有长期记录就缩成两条。
2. 旧提取结果先与当前原文件 size/mtime 或必要 hash 做 identity 比对；一致可作读取辅助，变化则重读。
3. 每个文件单独 read/distill/skip；先做 1–3 个有代表性的 canary，立即跑 G3/G4 结构和人工质量检查，确认解析与模板正确后再批量。
4. 每个有价值文件一份独立结果；重复版也有独立来源或具体 skip。敏感、噪声、不可读逐件 reason。
5. 21 个分组需要跨文件脉络时各写项目综合并链接本组结果；历史项目卡只作迁移证词，不能替代单文件读取。
6. G7 报告 expected/actual/diff、读/整理/跳过/未完成计数；机器校验与全量结构检查通过后，再做人工事实、特异性和脱敏复核。

不应做：只迁两条已有记录、用 19 张项目卡冒充 706 份文件处理、把历史 processed 状态写成当前 read，或把 summary 链接算作单文件结果。

完成证据：706 个 path 在 scope/inventory/manifest 一一闭合；每个 distilled 行有唯一文件结果；每个 skipped 行有具体 reason；21 个分组按需综合且链接有效；未完成项显式列出。

### 场景 2：多仓工作区只建导航

用户明确给出九个常用项目路径并说“只建索引”。现场有更多目录。

应做：只核验这九个路径；用用户说明、入口文档、源码布局和版本控制信息判目录类型与职责。项目总表及二级 README/inventory 只收九个；未指定目录不因扫描命中进入索引。到 G2 停止，不生成单文件结果。

完成证据：九个项目路径存在，分类证据与关键入口可回查，任何额外项目零命中。

### 场景 3：无 Git 的源码副本

用户说“把 `<工作区>/Project Beta` 加入知识库”。目录没有 `.git`，但有入口说明、构建清单、密集源码和测试布局。

应做：判为 code-project；普通模式冻结 README、设计/规范和必要入口，建立项目导航。若整理文档，建立唯一 `project-beta-docs` collection。未入选源码保持 out-of-scope，不伪写 skip。

不应做：因无 Git 判成文档资料，或默认逐文件总结所有源码。

### 场景 4：Git 管理的纯文档目录

用户说“把 `<资料根>` 及其全部文件收录”。目录有 `.git`，正文主要为 PDF/DOCX/XLSX 和主题子目录，没有源码布局。

应做：判为 document-collection；`.git/` 作为版本控制内部元数据排除并报告数量，其余用户内容文件逐件进入台账。

不应做：因有 origin 就创建代码项目有限 inventory。

### 场景 5：mixed 目录

一个根下同时有 `service/` 源码和 `research/` 文档。

- 普通“加入知识库”：根项目导航标 mixed-general；代码子树有限 inventory；`research/` 建独立不重叠 collection。
- 明确“及其下所有文件”：根 collection 唯一持有所有用户内容文件；`service/` 与 `research/` 仅作 group，不能再建重叠 collection。源码逐件 index-only skip，文档逐件 read/distill/skip。

完成证据：任一路径只有一个 owning collection，project inventory 只链接根 collection 和关键入口。

### 场景 6：单文件手动整理

用户指定一份 README 或设计文档。G1 冻结一个路径，G2 建最小唯一 collection，G3 读取，G4 产一份独立结果；没有跨文件关系则 G5 不写 summary。发现稳定跨项目结论时，只报告可另行保存的建议，不在本流程自动写入。

### 场景 7：文件更新和移动

- 路径不变但 size/mtime 变化：标 needs-review，重读后原位更新对应结果并复验。
- 路径移动：旧路径不能猜成新路径。先在 G1 更新 expected 和 group，再在 G2 调整台账；新 source 使用 portable-v1 生成新结果名。旧结果删除需用户授权。
- 路径缺失：inventory 标 missing，manifest 未完成或合法 skip 并写具体原因；不能悄悄移除。

### 场景 8：批处理中断

中断时交付已通过阶段的文件、当前门失败清单和剩余数。恢复时从最早未通过门继续；不要重写已通过且 identity 未变的结果，也不能把部分成功称为整个 collection 完成。

## 常见问答

### 1. 目录很大，能否只处理几个代表文件？

只有用户范围本来就是有限入口时可以。明确全量 collection 必须每个 inventory 文件逐件读取、整理或合法跳过；代表文件不能替代其他文件。

### 2. canary 是否总是必要？

单个清晰文本通常不值得。批量、混合格式、新解析器、敏感目录或迁移旧提取时先做少量首件校验，能在复制错误前拦住解析、模板或脱敏问题。

### 3. 可以抽样检查内容质量吗？

source、结构、内容特异的一句话、至少两个特异要点和模板空话必须逐份全量检查。人工对事实深度、领域准确性可增加风险抽样，但不能替代上述逐份门。

### 4. 历史摘要算 read 或 distilled 吗？

不算。先核验历史提取与当前原文件 identity；一致时提取可辅助 read，但 source 仍是原文件。distilled 只由真实独立单文件结果满足。

### 5. 完全重复的两个文件能共用一个结果吗？

不能。不同 source 各有独立结果，正文可明确其与主版本完全重复；也可在逐件比较后把低价值副本合法 skip，但必须具体说明。

### 6. 不可解析文件怎么处理？

先确认是否是临时解析器或权限故障。可修复故障停在 G3 修正；合同允许的永久受限、损坏或不支持格式才可合法 skip，并给具体 reason。

### 7. 敏感目录需要列出所有内容吗？

用户明确全量范围时，路径进入审计台账，但只读取最少必要元数据；凭据、合同细节、个人信息等逐件 restricted/skip，不复制正文。

### 8. 项目综合能替代单文件结果吗？

不能。综合负责跨文件事实和版本脉络；每个 distilled 文件仍必须有独立结果。没有结果、只有一个结果或没有跨文件综合价值时可以不建 summary；一旦存在，必须完整链接本组结果，漏链在 G5 打回。

### 9. 发现稳定方法时自动保存吗？

不自动。本流程只报告可保存为知识或经验的建议；用户明确要求进一步保存时，来源必须回到原文件，不能指向 summary。

### 10. manifest 指向结果但文件不存在怎么办？

G4 立即失败。恢复结果或把该行诚实退回未完成；不能让 dangling output 进入 G5/G7。

### 11. 结果目录出现 manifest 未引用文件怎么办？

这是孤儿结果，G4/G7 硬失败。核对其真实 source 后修台账或按授权清理；不得忽略。

### 12. scope、inventory、manifest 数量相同就够吗？

不够。必须比较完整 path 集合、唯一性、group、状态关系和输出双射；相同计数仍可能路径错位。

### 13. 文件名里含敏感信息怎么办？

台账需保留精确 source 才能审计，但面向用户的摘要和标题应最小暴露；slug 不得从敏感路径内容猜测。

### 14. 使用 portable-v1 会让旧结果失效吗？

显式只读 legacy 核验可让未改旧结果缺版本字段，并按 manifest 的 exact source/output 双射保留原名。正常新建或更新必须声明 portable-v1 并校验文件名 hash；更新旧结果需要迁移，若重命名未获授权就停止报告，不能自动切回 legacy。

## 完成证据

完整报告至少包括：

- expected/inventory/manifest 的 actual 和 set diff；
- 总文件、已读、已整理、合法跳过、未完成计数；
- 独立结果/source 双射、孤儿、重复 owner 和 summary 链接结果；
- UTF-8/BOM/尾随空白、敏感信息与长原文检查；
- 人工事实、内容特异性和脱敏检查结论；
- 每个失败的最早阶段、修正动作和下游重跑范围。

任一硬断言不为零就不能声称整体完成。可以交付已验证部分，但要用普通语言说清剩余项和下一步。
